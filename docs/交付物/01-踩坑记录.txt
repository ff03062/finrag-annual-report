              财报摘要 RAG 项目 · 踩坑记录（从新数据导入开始）
================================================================================
记录范围：从「放弃全量年报、改用 15 份摘要（new_Data）」开始，到本地 4B 模型跑通、
          双通道问答上线。
每条格式：现象 → 根因 → 解决 → 教训。

--------------------------------------------------------------------------------
一、数据与表格解析
--------------------------------------------------------------------------------

[坑 01] 全量年报 RAG「问什么都检索不到」
  现象：22,057 个 chunk 里 230 条含「营业收入」，向量 top10 全是员工人数、公司简介。
  根因：不是 chunk 大小问题，是「总营收 / 营收」这类口语词在年报正文里根本不存在，
        双塔 embedding 无法把口语映射到「营业收入」这个正式表述。
  解决：换数据（15 份摘要）+ 结构化通道（SQL 查指标），叙述通道只负责定性内容。
  教训：检索失败先看「语料里到底有没有这个词」，别急着调 chunk。

[坑 02] 表格结构不是「难」，是「规整」
  现象：担心 15 家公司的表格结构千奇百怪。
  实测：74 张表，主要会计数据表只有 3 种表头形态；指标行名去重后只有 13 个。
  解决：规则解析（纯函数），不用 LLM 读表。
  教训：先用数据说服自己，再决定要不要上模型。

[坑 03] 表头写「2025年」，但行是年末时点值
  现象：中微/华海/长电的「总资产」行，表头写 2025年/2024年。
  根因：表头只描述列，不描述行。总资产是存量（时点），营业收入是流量（期间）。
  解决：期间类型以「指标」为准（metric_dict 里定义 period_type），不信表头文字。
  教训：语义归属要跟「最小语义单元」（这里是行名）走。

[坑 04] 一张表里有两组表头（中芯国际、比亚迪、通达、宁德）
  现象：
        |            | 2025年末 | 2024年末 | 增减 | 2023年末 |
        | 总资产      | ...      | ...      | 4.0  | ...      |
        |            | 2025年   | 2024年   | 增减 | 2023年    |   ← 第二组
        | 营业收入    | ...      | ...      | 16.5 | ...      |
  解决：按表头行分组，每组管一段数据行；增减列（含「增减」）不入库。
  教训：表格的「行」不都是数据，也可能是表头——必须逐行判断。

[坑 05] 数字里带空格：`367, 718, 196` / `15, 213, 372, 100. 28`
  根因：PaddleOCR 在千分位和小数点后插了空格。
  解决：`normalize_number()` 去掉所有空白 + 千分位逗号 + 百分号，`-`/`--` 返回 None。
  验证：15 家营收全部能还原，四季度之和 = 年度值 45/45 通过。
  教训：脏数据先用「结构校验」验证，别靠肉眼抽查。

[坑 06] OCR 把行名拆成两行
  现象：通达动力「归属于上市公司股东」+「的净资产」，第二行数值全空。
  解决：除首列外全空的行，拼接到上一行首列。
  教训：先修复行，再解析列。

[坑 07] 单位写在表格外面
  现象：`单位：千元 币种：人民币` 在 <table> 之前的正文里，中芯/宁德是千元，其余是元。
  解决：从表格前 6 行文本里正则提取，入库时统一换算成「元」，同时保留 unit_raw。
  坑点：匹配单位必须按长度降序（亿元/万元/千元/元），否则「千元」会先命中「元」。
  教训：单位错一次，全表数字错 1000 倍，且很难被发现。

[坑 08] 跨公司对比时单位不一致
  现象：比亚迪（元）8039 亿 vs 中芯（千元）673 亿，若统一用第一行的单位会全错。
  解决：`format_rows()` 每一行输出自己的 unit_raw。
  教训：聚合查询是最容易暴露单位问题的地方。

[坑 09] 「不入库的表格」内容被整体丢弃（本项目最严重的设计缺陷）
  现象：问「恩捷股份主要产品生产技术情况」，答「未披露」；实际 md 里有完整三行表格。
  根因：chunker 把所有表格替换成一行占位符 `[表] 标题`，但只有 6 类表进 facts，
        产品技术/债券/公告这些表的内容永久丢失。
  解决：`table_to_text()` 把不入库的表转成文本（`行名：列名=值；列名=值`）保留在 chunk 里。
  教训：「结构化」不等于「可以丢掉原始内容」——没入库的必须留在检索层。

[坑 10] 短小节的标题丢失，导致永远检索不到
  现象：问「中芯国际的盈利模式」，答「摘要只披露主要会计数据」；但 md 里有「1. 盈利模式」。
  根因：`1. 盈利模式` 正文只有 57 字，被两级阈值（MIN_SECTION_CHARS=80 → merge<100）
        合并进上一块；标题只存在 section 字段，**向量化只看 text**，这个词没进索引。
  解决：① chunk 的 text 前面拼最后一级标题；② 阈值降到 40/50。
  验证：MRR@10 从 0.903 → 1.000。
  教训：元数据（section）不参与向量化，检索不到的内容等于不存在。

[坑 11] 表格转文本后块长超标（604 / 625 > 600）
  根因：`split_text` 保证 ≤600，但之后又拼标题（+20 字）。
  解决：切块预算改成 `MAX_CHARS - 40`；换行符也作为切分符。

二、存储与索引
--------------------------------------------------------------------------------

[坑 12] 「表格写哪去了」——三层存储要讲清楚
  SQLite `db/financial.db`
    - fact       681 条结构化数值（只来自主要会计数据/季度/股东总数 3 类表）
    - metric     12 个指标定义
    - table_meta 74 条表登记（title/type/unit/n_rows）—— 只有元信息，不含内容
  Milvus `db/milvus.db`
    - fin_report_chunks    512 条 chunk，text 字段存正文 + 表格文本
  教训：排查「数据在哪」之前，先看代码里到底写进了哪一层。

[坑 13] Milvus Lite 是单进程锁
  现象：后端在跑时，脚本连库报 `DataDirLockedError: another process holds the lock`。
  解决：调试脚本前先停后端；或改用新端点 `/chat/chunks` 在线查看。
  教训：Lite 适合开发，不适合「一边跑服务一边跑离线脚本」。

[坑 14] Milvus Lite 与 standalone 的 analyzer 不兼容
  现象：standalone v2.5.4 建表报 `failed to validate text schema`。
  根因：Lite 3.x 只认 `jieba`，standalone 2.5.x 只认 `chinese`。
  解决：`_analyzer_for(uri)` 按 endpoint 前缀自动选（http→chinese，本地路径→jieba）。
  教训：同一个库的两个发行版，能力集不一样，别假设 API 一致。

[坑 15] BM25 稀疏字段的索引 metric 必须是 BM25
  现象：`sparse field 'sparse' requires SPARSE_INVERTED_INDEX with metric BM25; got IP`。
  解决：`add_index("sparse", index_type="SPARSE_INVERTED_INDEX", metric_type="BM25")`。

[坑 16] collection 重启后处于 released 状态
  现象：`Collection 'fin_report_chunks' is in state 'released'; call load() before search`。
  解决：检索前 `load_collection()`，用模块级 flag 只调一次。

三、模型部署（rLLM-FinQA-4B）
--------------------------------------------------------------------------------

[坑 17] 官方没有 GGUF，全站唯一量化版是 macOS MLX
  实测：HF 只有 2 个 safetensors 分片（8.22 GB）+ 一个 MLX-4bit。

[坑 18] Ollama 在 Windows 上不能量化 safetensors
  现象1：`--quantize q4_K_M` → `unsupported --quantize "q4_K_M": supported types are int4, int8, nvfp4, mxfp4, mxfp8`
  现象2：`--quantize int4` → `MLX init failed: failed to load MLX dynamic library`
  根因：Ollama 的 safetensors 量化走 Apple MLX，Windows 没有这个库。
  解决：绕过 Ollama 的量化，自己用 llama.cpp 的 `llama-quantize.exe`。

[坑 19] f16 直接导入能跑但 OOM
  现象：`model requires 8.2 GiB but only 6.5 GiB are available`。
  说明：8GB 显存（4060 Laptop）装不下 8.8GB fp16。

[坑 20] 复用 Ollama 已经转好的 GGUF（省了一次转换）
  发现：Ollama 导入 safetensors 时内部已生成 GGUF，存在
        `D:\ollama_models\blobs\sha256-ab3e49fb...`（8.22 GB，magic = "GGUF"）。
  解决：直接拿这个 blob 跑 `llama-quantize.exe <blob> model-q4.gguf Q4_K_M`（56 秒，2.58 GB），
        再 `ollama create`（FROM 单个 gguf，**不加 --quantize**）。
  教训：卡住时先看工具内部产物，往往已经有可复用的中间件。

[坑 21] 从 safetensors 导入的模型模板是裸的，输出空
  现象：`ollama create` 成功后调用返回空字符串。
  根因：生成的 TEMPLATE 是 `{{ .Prompt }}`，没有 ChatML 特殊 token。
  解决：手写 Qwen3 ChatML 模板；或者换用自己转的、模板内嵌的 GGUF（推荐，它还保留 tool_call）。

[坑 22] num_ctx 不是越大越好
  实测：16384 → 100% GPU / 5.1 GB / 短问答 44–77 tok/s；
        32768 → prefill 3537→1041 tok/s，生成 65.6→24.7 tok/s，明显降速。
  结论：8GB 卡上 16384 是性价比拐点。

四、检索与路由
--------------------------------------------------------------------------------

[坑 23] Docker 版 Milvus 卡在 MinIO
  现象：`docker pull minio/minio` → `pull access denied`（quay / bitnami / 旧 tag 全失败）。
  根因：MinIO 2025 年撤掉 Docker Hub 镜像，而 Milvus standalone 依赖 S3 兼容存储。
  解决：改用 Milvus 2.5 的「etcd 内嵌 + 本地文件存储」单容器方案：
        ETCD_USE_EMBED=true / COMMON_STORAGETYPE=local
  （本地默认仍用 Milvus Lite，零依赖。）

[坑 24] 口语映射误伤正式指标
  现象：「中芯国际的盈利模式」被解析成「净利润」，走 SQL 答了 50.41 亿。
  根因：口语映射里 `盈利 → net_profit_attributable`。
  解决：有叙述意图（模式/情况/策略…）时禁用口语映射，只认正式别名。
  教训：口语映射要加前置条件，否则会吃掉同根的叙述词。

[坑 25] 多公司对比只答了一家
  现象：「比亚迪和中芯国际谁的净利润高」只返回中芯的数据。
  根因：`match_company` 只返回第一个命中。
  解决：`match_companies()` 最长匹配 + 命中后抹掉，返回全部；多公司时走 compare + both。

[坑 26] 追问丢失上下文
  现象：先问「恩捷 ROE」，追问「2024年的呢」，答「未披露」。
  根因：路由只看当前这一句，没有公司和指标。
  解决：`route(question, history_text)`，实体缺失时从最近 400 字历史里补。
  验证：追问 → 恩捷 + roe_weighted + 2024年 → -2.17%（正确）。

[坑 27] 「增速最快」被当成普通排名
  现象：问「2025年营收增速最快的是哪家」，返回营收排名（比亚迪第一）。
  解决：加 `growth` 通道，识别「增速/增长/同比/增幅」，用两年数据算 (curr-base)/|base|。
  验证：德福科技 +59.33%（与年报披露一致）。

五、生成与提示词
--------------------------------------------------------------------------------

[坑 28] 小模型的数字幻觉
  现象：qwen3:1.7b 把「322,045 户」写成「32,204,500 户」，还改单位成「亿元」。
  解决：纯数值题走「确定性渲染」（模板拼答案，0.0s、100% 准确，不经模型）。
  教训：数字不该交给 1-2B 模型转述。

[坑 29] 提示词写太死导致整体拒答
  现象：问「负债情况」，答「未披露」，但资料里有总资产和净资产。
  解决：规则改成「资料只覆盖一部分时，先答能答的，再说明缺什么」；
        同时把「举例」删掉（例子写得太具体等于教它答案）。
  教训：提示词写原则，不写案例。

[坑 30] 模型编造不存在的项目
  现象：答「参考资料中提及预计负债、长期借款、关联方应付」——grep 全部 15 份 md，
        这三个词一次都没出现。
  根因：旧提示词只禁止「推算」，没禁止「编造项目名」。
  解决：明确「不要编造任何项目名称或数字」；both 通道先出确定答案，模型只补定性。

[坑 31] 云端模型输出 Markdown 表格
  现象：前端是纯文本渲染，`|---|` 直接显示成乱码。
  解决：提示词加「输出纯文本，不要 Markdown 表格」。

[坑 32] 环境变量改了不生效
  根因：`chat_llm()` 用了 `@lru_cache`，客户端（含 key）被缓存；进程也读不到新的系统环境变量。
  解决：改完重启服务即可（不用重启电脑）；`LoadLLM._read_windows_env()` 还会读注册表兜底。

六、工程杂项
--------------------------------------------------------------------------------

[坑 33] Vite / uvicorn 只监听 IPv6
  现象：`netstat` 显示只有 `[::1]:8080`，curl 127.0.0.1 连不上。
  解决：vite `host: true`；uvicorn 用 `--host 127.0.0.1` 或浏览器直接访问 localhost。

[坑 34] 端口被占（WinError 10013）
  现象：自己起 uvicorn 报「以一种访问权限不允许的方式做了一个访问套接字的尝试」。
  根因：另有一个后端进程占着 8000（自动化验证时起的）。
  解决：`Get-CimInstance Win32_Process | Where CommandLine -match 'main.py'` 找出 PID 后停掉。

[坑 35] 下载大模型时 fake-ip 网关会挂起连接
  现象：16 并发 curl 全部 0 字节、无 TCP 连接；Python requests 线程永久阻塞。
  根因：本机 DNS 走 fake-ip（198.18.x.x）+ 代理，高并发时被挂起且不返回错误。
  解决：分块下载（8MB/块）+ 16 并发 + `timeout=(10,45)` 读超时自愈；失败块自动重试。
  实测：0.7 MB/s → 2.2 MB/s，8.22 GB 下完约 1 小时。

--------------------------------------------------------------------------------
七、意图识别（模型提议 / 代码裁决）
--------------------------------------------------------------------------------

[坑 36] 意图识别写成字符串遍历
  现象：标准问法都能过，换个说法就废（「这两家谁更能挣钱」解析不出公司）。
  根因：`if "营收" in question` 这类规则，能力上限就是那张词表。
        它只能覆盖你已经想到的说法，想到的越多规则越长，且永远补不完。
  解决：改成「小模型做 Schema Linking 出 DSL + 代码裁决」。
        模型负责理解（口语、省略、指代），代码负责决定（白名单校验）。
  代价：每个问题多约 1.2 秒（本地 4B + JSON 约束解码）。
        可 `INTENT_MODE=rule` 随时切回纯规则基线。

[坑 37] 把可用年份写死成 2025
  现象：问「中芯国际 2023 年营业收入」查不到数据。
  根因：财报摘要虽然标的是 2025 年，但表格里必然带**往年对比列**。
        库里实际有 2023、2024、2025 三个完整年度（2023/2024 各 112 条年度记录）。
        第一版写成 `VALID_YEARS = (2023, 2024, 2025)`，这已经算硬编码；
        更糟的是裁决时把范围外年份直接改成 2025 —— 会拿错年份的数字去回答问题。
  解决：新增 `chat/utils/datascope.py`，启动时查一次 SQLite 推导真实覆盖范围：
        `SELECT DISTINCT substr(period_label,1,4) FROM fact`
        喂给三处：Schema Linking 提示词、裁决器白名单、默认年份。
        用户明确问库里没有的年份时**保留原值**，让下游照实答「未披露」。
  实测：中芯国际 2023 年营收 = 45,250,425 千元（452.50 亿元）。

[坑 38] 小模型把「去年」算成 2023
  现象：「比亚迪去年赚了多少」返回 2023 年数据，正确是 2024。
  根因：模型不擅长相对时间换算，它拿训练语料的时间基准去推。
  解决：相对时间词（去年/前年/今年）一律由规则按 `REPORT_YEAR` 换算，不采信模型。
        年份的采信优先级固定为：问句里的明确年份 > 相对时间词 > 模型给的值。

[坑 39] 模型漏字段（口语它不认得）
  现象：「这两家谁更能挣钱」模型返回 `metric: null`，路由退化成文本检索。
  根因：口语映射（挣钱 → 净利润、家底 → 总资产）写在规则里，模型没见过这张表。
  解决：裁决器在 `metric` 为空且意图是数值类时，用规则的口语映射补一次。
        模型和规则各补各的短板，而不是二选一。

[坑 40] 模型会把 15 家公司全列出来
  现象：「哪家营收最高」模型把 15 家公司名全部填进 `companies`，
        SQL 变成 `IN (15 个)`，虽然结果对但没必要。
  解决：裁决器检测到 companies 覆盖了全部入库公司时，归一成空列表
        —— 语义就是「全库排名」，查询更省。

[坑 41] `format=json` 也不保证一定能解析
  现象：4B 模型偶尔输出 ```json 包裹、或前后带一句「好的，结果是：」。
  解决：`IntentDSL.parse()` 用正则提取第一个 `{...}`，并对字段做类型容错
        （year 传字符串、quarter 传 "Q2"、companies 传单个字符串都要接得住）。
        解析仍失败就返回 None，让上层回退规则路由，不让请求失败。

[坑 42] 裁决器单测的期望值写错，看起来像代码有 bug
  现象：16 条用例挂了 4 条，但实际行为是对的。
  根因：把「意图名」当成「通道名」写进期望值 —— `compare` 意图对应的
        通道是 `both`，`narrative` 意图对应的是 `rag`。
  教训：测的是「裁决输出 Route.channel」，期望值必须是通道名（sql/growth/rag/both/chat），
        不是意图名（query_metric/compare/...）。两层概念要分清。

[坑 43] e2e 断言只认「未披露」这一个词
  现象：越界题答案「现有资料**未提供**毛利率」被判 FAIL。
  根因：生成模型的措辞会变，断言词表太窄。
  解决：放宽到「未披露/未在/没有披露/未找到/无相关/不适用/未提供/未给出/未包含/不含/无法确认」。
        判据应该是「有没有编数」，不是「用了哪个词」。

================================================================================
一句话总结
================================================================================
这个项目里真正花时间的不是「写 RAG」，而是：
  1) 搞清楚数据到底长什么样（74 张表的真实结构，以及它们实际覆盖 2023–2025 三年，
     不是只有报告年那一年）
  2) 搞清楚每份数据该进哪一层（数值/SQLite、文本/Milvus、元信息/登记表）
