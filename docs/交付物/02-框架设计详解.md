# 财报摘要 RAG 问答系统 · 架构详解

> 面向 15 家 A 股半导体/新能源产业链公司 2025 年年度报告摘要。
> 本文档假设读者**从未看过这份代码**，按「怎么跑起来 → 为什么这样设计 → 每个文件干什么」组织。

## 0. 三十秒了解这个系统

**它在做什么**：用户问「中芯国际 2025 年营业收入是多少」或「比亚迪营收增长的原因」，
系统分别用 SQL 查数、用向量检索找原文，再由大模型组织成答案，流式吐回浏览器。

**三个关键判断**：

| 判断 | 理由 |
|---|---|
| **数字必须走 SQL，不能交给生成模型** | 小模型会把 `322,045 户` 写成 `32,204,500 户`，财务数字要求每一格都对 |
| **叙述必须走检索，不能只靠模型记忆** | 年报摘要里的事实模型不知道，必须从原文召回并标注来源 |
| **意图由模型理解，但由代码决定** | 模型的输出空间压缩成有限枚举，写错也只能在白名单里选错，不会越权查询 |

**五个核心概念**（后文都会展开）：

| 概念 | 一句话 |
|---|---|
| `fact` | 一行一个指标值，681 条，从 74 张 HTML 表格解析而来 |
| `chunk` | 一段正文/表格文本/图注，512 个，存进 Milvus 供向量检索 |
| `Route` | 一次查询的执行计划：走哪个通道、查哪家公司、哪个指标、哪一年 |
| `IntentDSL` | 模型输出的查询意图，`Route` 的前身，必须过裁决才能变成 `Route` |
| `adjudicate` | 裁决器，纯代码，把 DSL 里越界的字段丢弃或降级 |

**代码阅读顺序**（想快速理解，按这个顺序看）：

```
1. chat/controller/ChatController.py   HTTP 入口，SSE 怎么发出去
2. chat/service/ChatService.py         主链路，所有通道在这里汇合
3. chat/utils/QueryRouter.py           路由入口 resolve()
4. chat/utils/IntentDSL.py             DSL 定义 + 裁决器（核心）
5. chat/utils/TableQuery.py            参数化 SQL + 确定性渲染
6. chat/utils/MilvusRetriever.py       双链路检索
```

## 1. 系统全景

### 1.1 一次问答的完整路径

以「比亚迪 2025 年营业收入是多少」为例，从浏览器到答案：

```
① 浏览器 EventSource
   GET /chat/chat?question=...&historyId=0&token=<jwt>
        │
② ChatController.chat()
   ├─ verify_token() 校验 JWT（header 或 query 参数，因为 EventSource 不能设 header）
   └─ 包装成 StreamingResponse(text/event-stream)
        │
③ ChatService.chat()   ← 同步生成器，逐段 yield
   ├─ 取历史对话（historyId != 0 时查库，最多 3 轮）
   ├─ QueryRouter.resolve(question, history_text)
   │     ├─ SchemaLinker.link()          → 本地 4B 模型输出 JSON 意图 DSL
   │     ├─ IntentDSL.adjudicate()       → 裁决成 Route（白名单校验）
   │     └─ 失败则 QueryRouter.route()   → 纯规则兜底
   │
   ├─ 按 route.channel 分流
   │     ├─ "chat"   → 直接交给大模型答
   │     ├─ "sql"    → TableQuery 查库 + render_answer() 确定性渲染 → 直接返回
   │     ├─ "growth" → 查两年数据算同比 + render_growth() → 直接返回
   │     ├─ "both"   → 先输出 SQL 结果，再让大模型补充定性分析
   │     └─ "rag"    → Milvus 检索 + 大模型基于资料回答
   │
④ 追加来源，流式返回，每段包装成 SSE
   data: {"content": "比亚迪 2025 年营业收入为 8039.65 亿元……"}
   data: {"content": "来源：比亚迪：2025年年度报告摘要.md 第 2 张表"}   ← 代码追加，非模型生成
   data: {"content": "[DONE]"}
        │
⑤ 浏览器逐字渲染
```

**关键点**：`sql`、`growth` 两个通道的答案**不经过生成模型**，由 `TableQuery.render_answer()`
用模板拼出来。这是数值准确性的根本保障，延迟也因此只有 1.1–1.3 秒（其中 ~1.2 秒是意图识别）。

## 2. 意图识别：模型做提议者，代码做裁决者

这是整个系统最需要讲清楚的部分，也是最近一次重构的重点。

### 2.1 为什么不用纯规则

早期实现是 `QueryRouter.route()` 里做字符串遍历：`if "营收" in question` → 走 SQL。
问题是**规则的能力上限就是那张词表**：

| 用户说法 | 纯规则的结果 |
|---|---|
| 比亚迪去年赚了多少 | 「赚」不在正式别名里，可能匹配失败 |
| 这两家谁更能挣钱 | 「这两家」指代无法解析 |
| 哪家现金流最健康 | 「最健康」不是任何枚举值 |
| 中芯国际毛利率 | 匹配不到任何指标 → 走 RAG，行为对但路径是碰巧 |

规则好写、可解释、零延迟，但它只能覆盖**你已经想到的说法**。真正需要的是理解能力。

### 2.2 折中：让模型只做「受限分类」

直接让模型生成 SQL 有两个问题：自由度过大（等于给它整库权限）、不可校验。
所以把模型的输出空间压成一个**枚举驱动的 DSL**：

```python
@dataclass
class IntentDSL:
    intent: str                    # 六选一，枚举
    companies: list[str]           # 必须是 15 家之一
    metric: str | None             # 必须是 13 个 metric_code 之一
    year: int | None               # 数字
    quarter: int | None            # 1-4 或 None
    aspect: str | None             # 自由文本，但只用于提示，不参与查库
    confidence: float
```

`intent` 的六个取值及含义：

| intent | 含义 | 落到哪个通道 |
|---|---|---|
| `query_metric` | 问某公司某指标的数值 | `sql`（有 aspect 时 `both`） |
| `compare` | 多公司对比、排名、最值 | `both` |
| `growth` | 同比、增速、增长幅度 | `growth` |
| `narrative` | 业务、原因、行业地位、风险 | `rag` |
| `chitchat` | 问候闲聊 | `chat` |
| `out_of_scope` | 问的指标不在库里（毛利率、存货…） | `rag`（回答未披露） |

模型**能表达的全部内容就是这个结构**。它不写 SQL、不产生数字、不能指定表名或列名。

### 2.3 Schema Linking：把枚举喂给模型

`chat/utils/SchemaLinker.py` 构造的提示词只包含三样东西：

```
可查询公司（companies 只能填下面的简称）：
比亚迪、宁德时代、中芯国际、……（15 家，来自数据库实际入库的公司）

可查询指标（metric 只能填 code）：
total_assets=总资产、net_assets_attributable=归属于上市公司股东的净资产、……（13 个）

期间范围（数据库实际覆盖的范围）：
年度数据：2023 / 2024 / 2025
季度数据：仅 2025 年的 净利润、扣非净利润、经营现金流、营业收入
```

**没有任何数值，没有任何表结构，没有任何 SQL 片段。**

调用方式（`ai/LoadLLM.py: schema_llm()`）：

```python
ChatOllama(
    model="rllm-finqa-4b:q4",
    streaming=False,
    format="json",        # 强制 JSON 输出，避免 4B 模型跑偏成散文
    temperature=0,        # 要稳定，不要创意
    num_ctx=16384,        # 与主模型一致，避免 Ollama 反复卸载重载
)
```

### 2.4 裁决器：模型的提议必须过这道关

`chat/utils/IntentDSL.py: adjudicate()` 是纯代码、零延迟、可单测。
它的职责是**把模型的任何输出收敛成安全可执行的 Route**：

| 情况 | 裁决动作 |
|---|---|
| 公司不在 15 家白名单 | 丢弃该实体（不做模糊猜测） |
| 指标不在 13 个 code 内（「毛利率」） | `metric=None` → 意图降级 → 走文本检索答「未披露」 |
| 模型漏了指标（「挣钱」） | 用规则的口语映射补上 `net_profit_attributable` |
| 模型把「去年」算成 2023 | 相对时间一律由规则按报告年换算，**不采信模型** |
| 年份超出库内覆盖 | 用户明确问才保留（照实答未披露）；模型凭空编的则回落默认年 |
| 季度但该指标无季度数据 | 丢掉季度，退化为年度（如总资产只有年末值） |
| `query_metric` 但没给公司 | 转成 `compare`（可能是在问排名） |
| `compare` 但没给指标 | 降级成 `narrative` |
| 模型返回 15 家全部公司 | 归一成空列表，语义就是「全库排名」，查询更省 |
| 输出不是合法 JSON / 模型没启动 | 整个 `resolve()` 回退纯规则 |

裁决完输出 `Route`：

```python
@dataclass
class Route:
    channel: str                       # sql | growth | rag | both | chat
    company: str | None                # 单公司
    companies: list[str] | None        # 多公司（≥2 家时填这里，company 留空）
    metric: str | None
    period_label: str | None           # "2025年" / "2025年末" / "2025Q1"
    year: int | None
    quarter: int | None
    intent: str | None                 # 来自 DSL 的原始意图，仅用于观测
    source: str                        # "llm" 或 "rule"，标记谁产出的
```

`source` 字段很关键：日志里能直接看出这条路由是模型给的还是规则兜底的。

### 2.5 三层降级

```
第 1 层  模型 Schema Linking → DSL → 裁决 → Route      （默认，source="llm"）
   ↓ 模型未启动 / 超时 / JSON 非法
第 2 层  纯规则 route() → Route                        （source="rule"）
   ↓ 规则也没命中公司或指标
第 3 层  channel="rag" 全库检索 → 大模型基于资料回答
```

这三层互不依赖，任何一层挂掉都不会让请求失败。

### 2.6 代价

意图识别中位 **1.17 秒**（本地 4B + JSON 约束解码），SQL 通道因此从 0.0–0.3s 变成 1.1–1.3s。
这是「用模型做理解」的真实成本。若需压掉，`.env` 里 `INTENT_MODE=rule` 可切回纯规则基线。

## 3. 数据层

### 3.1 三层存储

| 层 | 引擎 | 存什么 | 规模 |
|---|---|---|---|
| 结构化数值 | SQLite `db/financial.db` | 681 条事实 + 12 指标 + 74 张表登记 | 0.29 MB |
| 文本与表格 | Milvus `fin_report_chunks` | 512 个 chunk（正文 + 表格文本 + 图注） | ~4 MB |
| 原始文件 | `new_Data/` | 15 份 md + 72 张图 | 3 MB |

### 3.2 SQLite 表设计

#### `fact` —— 一行一个指标值（681 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `company` | TEXT | 公司简称，如「中芯国际」 |
| `company_code` | TEXT | 股票代码，如 `688981` |
| `report_year` | INTEGER | 2025 |
| `metric_code` | TEXT | 指标编码，见 `metric` 表 |
| `period_type` | TEXT | `point_in_time`（时点）/ `duration`（期间） |
| `period_label` | TEXT | `2025年` / `2025年末` / `2025Q1` |
| `period_start` | TEXT | 期间开始，时点为 NULL |
| `period_end` | TEXT | 期间结束，统一 12-31 |
| `value_num` | REAL | 原始单位下的数值 |
| `value_yuan` | REAL | 换算成「元」的值（比率/股数为 NULL） |
| `unit_raw` | TEXT | `元` / `千元` / `万元` / `户` |
| `unit_kind` | TEXT | `currency` / `ratio` / `per_share` / `count` |
| `source_doc` / `source_table` / `source_row` / `source_col` | — | 溯源：哪份文件、第几张表、第几行第几列 |
| `raw_text` / `raw_header` | TEXT | 原始单元格文本与列名（调试用） |

约束：`UNIQUE(company, metric_code, period_label)`；
索引：`(metric_code, period_end)` 和 `(company, metric_code)`。

#### `metric` —— 指标维表（12 行，唯一指标定义源）

```python
"revenue": {
    "name_cn": "营业收入",
    "aliases": ["营业收入", "营收", "总营收", "主营业务收入", "收入"],
    "period_type": "duration",      # 决定期间标签是「2025年」还是「2025年末」
    "unit_kind": "currency",        # 决定展示格式与是否换算
}
```

12 个指标：`total_assets`、`net_assets_attributable`、`revenue`、`total_profit`、
`net_profit_attributable`、`net_profit_deducted`、`ocf_net`、`roe_weighted`、
`eps_basic`、`eps_diluted`、`rd_revenue_ratio`、`shareholder_total`。

另有一个**派生指标** `total_liabilities`（负债合计）：库里没有直接披露，
由 `total_assets − net_assets_attributable` 推算，查询时优先找真实值、找不到才算，并在答案里标注「推算」。

#### `table_meta` —— 表格登记（74 行）

只记元信息（哪家公司、哪份文件、第几张表、标题、类型、单位、行数），**不含表格内容**。
内容在 Milvus 的 `text` 字段里。

### 3.3 Milvus Collection

Collection：`fin_report_chunks`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT64 PK | 自增 |
| `company` | VARCHAR(64) | 标量过滤主力 |
| `company_code` | VARCHAR(16) | |
| `report_year` | INT32 | 标量过滤 |
| `section` | VARCHAR(1024) | 标题路径，`>` 连接 |
| `chunk_type` | VARCHAR(32) | `narrative` / `table_summary` / `figure` |
| `doc_path` | VARCHAR(512) | 溯源 |
| `img_path` | VARCHAR(512) | 图注块对应的图片 |
| `table_ref` | VARCHAR(64) | 关联的结构化表编号 |
| `text` | VARCHAR(4096) | 正文，开启 analyzer |
| `dense` | FLOAT_VECTOR(768) | bge-base-zh-v1.5 |
| `sparse` | SPARSE_FLOAT_VECTOR | 由 BM25 Function 自动生成 |

索引与函数：

```python
dense  : FLAT,  metric=IP          # 512 条数据量小，FLAT 精确检索比 IVF 更合适
sparse : SPARSE_INVERTED_INDEX, metric=BM25   # 必须 BM25，稠密/稀疏才能统一进 RRF
Function: BM25(input=["text"], output=["sparse"])   # 写入时自动生成稀疏向量
```

**分析器随部署模式自动切换**（`create_data/build_index.py: _analyzer_params_for`）：

| 部署 | analyzer | 原因 |
|---|---|---|
| Milvus Lite（本地文件） | `{"type": "jieba", "filter": [...]}` | Lite 支持 jieba 插件 |
| Milvus standalone（HTTP） | `{"type": "chinese", "filter": [...]}` | standalone 不支持 jieba，只能用内置中文分析器 |

### 3.4 数据覆盖范围（datascope）

**这是踩过的坑**：不能把可用年份写死。

财报摘要虽然标的是 2025 年，但表格里必然带**往年对比列**（本期/上期、2025/2024）。
库里实际有 2023、2024、2025 三个完整年度 —— 2023、2024 各 112 条年度记录、30 条时点记录。

所以 `chat/utils/datascope.py` 在启动时查一次 SQLite：

```sql
SELECT DISTINCT substr(period_label, 1, 4) FROM fact                        -- 年度覆盖
SELECT DISTINCT substr(period_label, 1, 4) FROM fact WHERE period_label LIKE '%Q%'  -- 季度覆盖
SELECT DISTINCT metric_code FROM fact WHERE period_label LIKE '%Q%'         -- 哪些指标有季度值
SELECT DISTINCT company FROM fact ORDER BY company                          -- 实际入库的公司
```

实测输出：

```
[数据范围] 年度数据：2023/2024/2025
           季度数据：net_profit_attributable、net_profit_deducted、ocf_net、revenue（仅 2025）
```

这份范围同时喂给三处：Schema Linking 的提示词、裁决器的白名单、默认年份的选取。
明年接入 2026 年报时，代码不用改。

## 4. 离线构建

在线服务不碰这条链路。入口统一是 `create_data/build_index.py`：

```bash
python create_data/build_index.py --sqlite          # HTML 表格 → facts → SQLite
python create_data/build_index.py --milvus          # md 正文 → chunks → Milvus
python create_data/build_index.py --all --llm-fallback   # 两者都建，开启 LLM 兜底
python create_data/build_index.py --dry-run         # 只解析不写库
```

### 4.1 表格解析（规则优先）

```
HTML → grid（展开 colspan/rowspan）
     → repair_rows（合并 OCR 拆断的行）
     → detect_header_groups（一个表头行 + 它管辖的行范围）
     → 按指标取列（期间类型以 metric 为准，不看表头文字）
     → normalize_number（去空格/逗号/%）
     → 单位换算（千元 ×1000、万元 ×10000）
```

**关键设计：期间类型由指标定义决定，不由表头决定。**
表头写着「2025年」，但「总资产」是年末时点、「营业收入」是年度区间。
照抄表头会把总资产标成 `2025年`，与季度数据混淆；用指标定义覆盖才正确。

**增减列不入库**：可由两年数值反算，且口径混乱（`16.5` / `12.83%` / `增加0.9个百分点`）。

### 4.2 三重校验

| 校验 | 方法 | 实测 |
|---|---|---|
| C1 | 四季度之和 == 年度值 | **45/45 通过**（15 家 × 营收/净利润/经营现金流） |
| C2 | 增减% 可由两年数值反算 | 13/15 精确，2 家为四舍五入差异 |
| C3 | 与正文披露数字交叉比对 | 抽样通过 |

C1 是最强的一道：任何列错位、单位错乱、数字截断都会让等式不成立。

### 4.3 LLM 表格兜底

15 份摘要的表格全部能被规则解析（681 条、0 警告），但生产环境会遇到没见过的表
（合并单元格、多组表头、多余列）。这时不抛异常，也不让模型从零读表：

```
规则解析 → 校验 → 通过 → 入库
              │
              └─ 失败 → LLM 输出「列语义 + 行映射」（不含数值）
                        → 代码按标注重新取数 → 再校验 → 仍失败进人工队列
```

触发条件：T1 表头识别失败 / T2 列数 ∉ {4,5} / T3 指标命中率 < 60% / T4 四季度和不等于年度值。

**边界（这是设计的关键）**：

- 模型输入只有表头文字和行名文字，**一个数值都不给**
- 模型输出只有结构（哪列是哪年、哪行是哪个指标），不产生任何数字
- 数值仍由 `normalize_number` 从原格子取，期间类型仍以 `metric_dict` 为准
- 拿到标注后**必须重新校验**，不通过就进人工队列

实测（`tests/test_llm_fallback.py`）：给中芯国际主表人为加一列「备注」触发 T2，
模型返回 `confidence=0.98`、2 组表头、11 行，修复后三个关键指标与正常表完全一致。

### 4.4 切块

| 参数 | 值 | 依据 |
|---|---|---|
| 切分单位 | 标题（H1–H6 任一变化） | 15 家标题体系不统一，按层级切更鲁棒 |
| 目标块长 | 400 字 | 段落 p90 = 252，一块装 1–2 段 |
| 重叠 | 60 字 | 一个句子长度 |
| 硬上限 | 600 字（预留 40 字给标题） | |
| 短节阈值 | 40 字 | 低于此并入相邻块 |

产物 512 块：`narrative 395 + table_summary 45 + figure 72`（Milvus 实测分布）。

**关键细节**：chunk 的 `text` 前面必须拼上最后一级标题。
否则短节被合并后标题只留在 `section` 元数据里，而向量化只看 `text`，这个词就永远检索不到。

**表格处理**：
- 已入 `fact` 的表 → 正文留占位符 `[表] 标题`（避免和 SQL 通道重复）
- 未入库的表 → `table_to_text()` 转成文本保留（否则内容永久丢失）

## 5. 检索

`chat/utils/MilvusRetriever.py: search()`

### 5.1 双链路

| 链路 | 实现 | 负责 |
|---|---|---|
| 稠密 | `bge-base-zh-v1.5`（768 维），召回 50 条 | 语义（"赚钱能力" ↔ "净利润"） |
| 稀疏 | Milvus 内置 BM25，召回 50 条 | 字面（"GaN"、"注 1"、"第一大股东"） |

两路都支持标量过滤（`company == "中芯国际"`），且过滤**下推到 ANN 之前**，不是先检索再筛。

### 5.2 RRF 融合

```python
client.hybrid_search(
    reqs=[dense_req, sparse_req],
    ranker=RRFRanker(k=60),
    limit=20,
)
```

为什么不用加权求和：稠密相似度（0~1）和 BM25 分数（0~20+）量纲不可比。
RRF 只用排名，`score = Σ 1/(k + rank)`，参数只有 k，不需要调权重。

### 5.3 精排

`bge-reranker-large`（cross-encoder）对融合后的 20 条做 query-doc 交互打分，取 top-8 进 prompt。

- 双塔模型：query 和 doc 分别编码，只能判断「语义接近」
- cross-encoder：拼起来读，能判断「是否回答了问题」

实测：`Recall@5 = 100%`，`MRR@10 = 0.944`。

## 6. 答案生成

### 6.1 通道分工

| 通道 | 数据来源 | 谁来组织答案 | 典型耗时 |
|---|---|---|---|
| `sql` | SQLite 单公司单指标 | **模板渲染，不经模型** | 1.1–1.3s |
| `growth` | SQLite 两年数据 | **模板渲染，不经模型** | ≈1.2s |
| `both` | SQL + Milvus | SQL 部分模板渲染，叙述部分大模型补充 | 12–45s |
| `rag` | Milvus | 大模型基于资料回答 | 10–27s |
| `chat` | 无 | 大模型直接回答 | 1–3s |

### 6.2 确定性渲染

`TableQuery.render_answer()` 把查询结果拼成中文句子：

```
中芯国际 2025年营业收入为 673.23 亿元（原文 67,323,192 千元）。
```

副作用是**零幻觉**：既然没经过生成模型，数字就不可能被改写。
代价是句式固定，但这恰恰是数值题想要的。

### 6.3 `both` 通道的「先答后补」

多公司对比时，模型容易把推算值说成披露值，也会改写数字。所以拆成两段：

```
第 1 段：SQL 排名 + 模板渲染 → 直接 yield 给用户（数字已确定）
第 2 段：route.channel 改为 "rag_brief"，让模型只补充定性分析
```

`ChatService.BRIEF_HINT` 明确要求模型：
「上面的结构化答案已经输出给用户了，你**只补充资料里关于该指标的定性信息**，
不要再复述任何数字，也不要重复结论。」

### 6.4 生成模型的提示词约束

`ChatService.PROMPT_TEMPLATE` 里 8 条规则，重点几条：

- 数字必须来自「结构化数据」或「文本资料」，不要凭空编造
- 两者冲突时以结构化数据为准（正文数字常有四舍五入）
- 资料只覆盖问题的一部分时，先回答能回答的部分，再说明缺什么，不要整体拒答
- **输出纯文本**，不要 Markdown 表格

还有一段 `COMPLIANCE_RULES`，解释财报合规标记的含义：
「不适用」表示按规则无需披露，**不是数据缺失**；「否」是对前面问句的否定回答；
「无」「-」表示单元格为空，**不是数值 0**。这些词搞错，答案就会把「不适用」说成「没披露」。

### 6.5 答案溯源

每个答案末尾都标出处。格式按通道分两种：

**数值题**（`sql` / `growth`）—— 标到「哪份文件的第几张表」：

```
中芯国际 2025年营业收入为 673.23 亿元（原文 67,323,192 千元）。
来源：中芯国际2025年年度报告摘要.md 第 3 张表
```

**叙述题**（`rag`）—— 标到「哪份文件的哪一节」，去重后最多 3 条：

```
（模型基于资料生成的回答）

来源：1. 中芯国际2025年年度报告摘要.md §一、行业地位；2. 比亚迪：2025年年度报告摘要.md §二、风险因素
```

**对比题**（`both`）—— 前后两段各有来源，用不同前缀区分，避免混在一起：

```
营业收入（2025年）排名：...
来源：比亚迪：2025年年度报告摘要.md 第 2 张表 等 15 份     ← 数值来自表格

（模型补充的定性分析）

参考资料：1. 比亚迪：2025年年度报告摘要.md §经营情况讨论与分析   ← 文字来自正文
```

#### 三条设计约束

**1. 来源由代码生成，不让模型写。**
`PROMPT_TEMPLATE` 规则 8 至今写着「不要输出「来源1」「参考资料」这类字样」，
不是忘了加，而是故意的：模型会编造不存在的来源，也会把编号抄到错误的句子上。
代码给的是它**实际查库或实际检索到的那条记录**，100% 准确。

**2. 推算值不标来源。**
`total_liabilities`（负债合计）不在摘要披露范围内，是「总资产 − 归属于上市公司股东的净资产」算出来的。
给它标「第 3 张表」会让人以为表格里真有这一行，所以它只有推算口径说明：

```
中芯国际 2025 年末负债合计约 2,168.94 亿元（**推算值**）。
（推算值 = 总资产 − 归属于上市公司股东的净资产；该口径把少数股东权益也计入负债，仅供量级参考）
```

**3. 文件名必须归一。**
`new_Data/` 下的文件命名是「公司名：原始文件名.md」，但部分原始文件名自身也含公司名，
个别还带着 OCR 转换后缀：

```
中芯国际\中芯国际：中芯国际2025年年度报告摘要.md
华海清科\华海清科：2025年年度报告摘要.pdf_by_PaddleOCR-VL-1.6.md
```

直接展示会变成 `来源：中芯国际：中芯国际2025年…`。`TableQuery.doc_label()` 负责：
去掉 `公司名：` 前缀 → 抹掉 `.pdf_by_*` 后缀 → 若此时丢了公司名再加回去。

#### 来源数据在哪

溯源字段一直都在，只是之前没渲染到答案里：

| 层 | 字段 |
|---|---|
| `fact` 表 | `source_doc` / `source_table` / `source_row` / `source_col` |
| `chunk` | `doc_path` / `section` / `img_path` |
| `query_metric` / `query_compare` 返回值 | 每行带 `source_doc` + `source_table` |
| `query_growth` 返回值 | 同上（原先没查这两个字段，已补） |

各通道的实现位置：

| 通道 | 追加来源的函数 |
|---|---|
| `sql` / `both`（数值段） | `TableQuery.render_answer()` → `_with_lineage()` |
| `growth` | `TableQuery.render_growth()` → `_with_lineage()` |
| `rag` / `both`（叙述段） | `ChatService._sources_text()`（`_rag_channel` 把命中的 `Document` 收进 `rag_docs`，链结束后统一追加） |

## 9. 部署

| 组件 | 本地开发 | 生产演示 |
|---|---|---|
| 向量库 | Milvus Lite（`db/milvus.db`，零依赖） | `docker compose -f docker-compose.milvus.yml up -d`（单容器） |
| 结构化库 | SQLite 文件 | 可换 MySQL/PostgreSQL |
| 意图识别 | 本地 Ollama `rllm-finqa-4b:q4` | 同左（可 `INTENT_MODE=rule` 关掉） |
| 答案生成 | DashScope `qwen3.8-max-0902` | 同左 |

**切换向量库**只需改 `.env` 的 `MILVUS_ENDPOINT`：

```ini
MILVUS_ENDPOINT = "D:\workspace\MultiCrop-FinRAG\db\milvus.db"   # Lite
MILVUS_ENDPOINT = "http://127.0.0.1:19530"                       # standalone
```

两种模式的**数据不共享**，切换后必须重跑 `build_index.py --milvus`；
分词器随 URI 自动切换（Lite → jieba，standalone → chinese）。

**为什么用单容器 compose**：官方三容器版依赖 MinIO，而 MinIO 在 2025 年撤掉了 Docker Hub 镜像。
Milvus 2.5 支持 `ETCD_USE_EMBED=true` + `COMMON_STORAGETYPE=local`，一个容器即可跑通。

可视化：`docker run -d -p 3000:3000 -e MILVUS_URL=http://127.0.0.1:19530 zilliz/attu:v2.5`，
浏览器打开 `http://127.0.0.1:3000`，在 Data 页可翻看全部 512 个 chunk。
