# 简历速问速答（25 条）

> 用法：**带 ★ 的 8 条是必背项**，几乎每场技术面都会问到；其余按面试官兴趣挑。
> 每条答案都对应仓库里的真实实现，括号里是能现场打开佐证的文件。

---

## 一、架构与选型

### ★ Q1 数字都在库里，为什么不全部走 SQL？

因为库里只覆盖年报摘要里的主要会计数据（681 条事实），而用户一半的问题在正文里——"储能业务进展""毛利率为什么降""行业地位如何"，SQL 查不到。反过来，问"宁德时代 2025 年营收"这种，走 RAG 就是把已经精确的数字交给模型复述，必错。所以不是二选一，是**按问题类型分流**：能确定答案的不进模型，只能检索的才进模型。
（`chat/utils/QueryRouter.py` 分流，`chat/service/ChatService.py` 两条通道）

### ★ Q2 双链路里 BM25 到底补了什么？稠密向量不够吗？

稠密向量对**字面精确**的东西不敏感：专有名词、表号（"注 1"）、财务长实体（"归属于上市公司股东的扣除非经常性损益的净利润"）。768 维压不下这种长串，容易和"净利润"混为一谈，而这两个数差一个量级。BM25 靠词频和 IDF 正好兜住字面。两路各召 50 条，RRF 融合取 20。
（`chat/utils/MilvusRetriever.py` 第 70–92 行）

### Q3 为什么用 RRF，不直接对两路分数加权求和？

两路分数量纲不可比：IP 相似度是 0–1，BM25 可以到 20 以上。加权求和必须先归一化，而归一化系数依赖当次查询的分数分布，换一个问题就得重调。RRF 只用**排名**：`1/(k+rank)`，k=60，天然量纲无关，一个参数吃所有查询。
（同上，`RRFRanker(RRF_K)`）

### Q4 都有双塔向量了，为什么还要 reranker？

双塔是 query 和 doc **分别**编码，只能判断"语义接近"；cross-encoder 把两者拼起来读一遍，才能判断"这段是否回答了这个问题"。代价是每个候选一次前向，所以只对 RRF 融合后的 20 条做，精排取 top-8 进 prompt。20 → 8 这个量级上，收益远大于延迟。
（`bge-reranker-large`，`RERANK_TOP=8`）

### Q5 为什么是 Milvus，不是 Chroma 或 FAISS？

三个硬需求：① 原生支持稀疏向量和库内 BM25 function，两路能用**一次** `hybrid_search` 完成，不用应用层跑两套检索再拼；② filter 能下推到 ANN 之前，公司/年份过滤在索引层做，不是召回完再筛掉；③ 同一套代码在 Milvus Lite（本地一个文件、零依赖）和 standalone（Docker）之间切，只改 `MILVUS_ENDPOINT`。FAISS 没有标量过滤和 BM25，Chroma 不支持稀疏 + 库内 RRF。

## 二、意图识别（这份简历的核心）

### ★ Q6 为什么不让模型直接生成 SQL？

两个原因。**能力**：本地跑的是 4B 量化模型，让它写 JOIN 和 CASE WHEN，错在语法和字段上，你既没法定位也没法兜底。**风险**：一旦模型能写 SQL，它就掌握了"查什么、查哪年、怎么聚合"的决定权，错一次就是一个看起来合理的错数字，而且静默。现在的边界是——模型只能填 6 个字段的 JSON，每个字段的值必须落在枚举里，落不进去就被裁决掉。它一个数字都碰不到。
（`chat/utils/SchemaLinker.py` 的 PROMPT，`chat/utils/IntentDSL.py` 的 `adjudicate`）

### ★ Q7 "代码裁决"具体裁什么？举三个例子。

① 模型返回"阿里巴巴"→ 不在 15 家白名单，公司字段直接丢弃，降级文本检索。
② 模型返回 metric="毛利率"→ 不在 13 个指标 code 里，指标置空，意图从 `query_metric` 改判 `narrative`。
③ 模型给 `query_metric` 却没给公司 → 语义不自洽，改判 `compare` 走全库排名。
另外 `compare`/`growth` 缺指标降级文本，`out_of_scope` 一律走 RAG。24 条单测覆盖了这些分支。
（`tests/test_intent_dsl.py`）

### Q8 意图识别 1.17s，为什么不做规则快路径把它压到毫秒？

想过，否了。双路由会让"什么时候走规则、什么时候走模型"变成新的硬编码判断——等于把要消灭的问题换个位置藏起来；而且两条路的输出格式和置信度不可比，线上出问题无法归因。1.17s 相对整条链路（RAG 通道 10–27s）不是瓶颈，用户根本感知不到。要优化也该优化检索和生成，不是意图。

### Q9 模型怎么知道"去年"是哪一年？

不让它知道。相对时间由代码算：`前年=−2 / 去年=−1 / 今年=0`，从问题原文匹配，再结合报告年份推算。prompt 里只告诉它"提到年份就填那一年，没提就填 2025"，它对"现在是什么时候"没有任何概念。**让模型算时间，跨年、跨会话必漂。**
（`IntentDSL._relative_year`）

### Q10 模型编造一个不存在的公司怎么办？

白名单挡两道。第一道在 prompt：只列 15 个简称。第二道在裁决：`resolve_company` 先查别名表（中芯 → 中芯国际、CATL → 宁德时代），再判断是否是白名单全称的子串，都不是就返回 None，字段丢弃、降级检索。全称也能认（"云南恩捷新材料股份有限公司"→ 恩捷股份），但只能认白名单里的。

### Q11 用户问"毛利率"，库里没有，怎么答？

`out_of_scope`，裁决直接把通道改成 RAG。毛利率不在可查指标里，但年报正文通常有"毛利率变动原因"的叙述，能答出定性结论。关键是**别让它掉进 SQL 通道返回"未披露"**——那会让用户以为年报没写这件事，而实际上写了，只是不在这张表里。
（可查 12 个指标 + 1 个派生，派生的是总负债 = 总资产 − 净资产）

## 三、数据链路

### ★ Q12 681 条事实是怎么来的？怎么保证没取错？

两条路各读一遍，再对账。

**OCR 路**：md 里的 HTML 表格 → 网格展开（合并单元格拆平）、多组表头识别、断行修复 → 按指标别名取数。
**VLM 路**：PyMuPDF 的 `find_tables()` 检出表格 bbox → 裁成图（跨页的拼成一张）→ 视觉模型读数。

两路按 `(指标, 期间)` 配对——**不是按“第几张表”对**，因为 md 的表序号和 PDF 的页码表序是两套编号，硬映射只会引入新错误。值一致标 `both`；只有一路的带 `source` 入库；对不上进 `fact_conflict`，**不入库**。

结果：**681 条里 665 条两路独立读出完全一致**，15 条只有 OCR（股东总数是 kv 文本，不在裁图里），**1 条冲突被拦下**——华海清科 Q3 经营现金流，OCR 读 29,519,005.37、VLM 读 29,510,005.37（把 9 看成 0），看图确认 OCR 对，这条不进库，所以最终入库 680 条。再叠一层 C1 恒等式兜底：2025 年四季度之和必须等于年度值，45/45 全过。
（`create_data/reconcile.py` + `table_parser.validate_facts`）

### ★ Q13 财报表格里带"上年同期"列，怎么保证不取错年份？

这是最容易错的地方，也是我特意处理过的地方。一份 2025 年报的表格，列经常是"2025年 / 2024年 / 增减%"，如果按列序取第 2 列，取到的就是 2024 的数。做法是**以表头文字为准，不按列序**：把"本期 / 上期 / 本年 / 上年"映射成具体年份，再和 `period_label` 对齐。所以库里的 2023、2024 数据，全部是从 2025 年报的对比列里取出来的，不是从 2023/2024 年报里取的——因为我们手上的数据源就是 15 份 FY2025 摘要。

### Q14 RAG 检索为什么不按年份过滤？库里有 `report_year` 啊。

代码里明确传 `year=None`。因为库里只有 2025 年那一份摘要，而用户问题里的年份经常是**内容**不是**报告年份**——"2024 至 2030 年的产能规划""对比 2023 年的数据"，一过滤就全滤没了。公司名照常过滤（同一问题不会跨公司问叙述），年份交给语义匹配。
（`ChatService._rag_channel` 的注释就写着这个理由）

### Q15 15 家公司，为什么只有 514 个 chunk？是不是切太粗？

数据源是**年报摘要**不是完整年报，一份摘要正文就几千字。切分参数是：目标 400 字、重叠 60 字、硬上限 600 字、短叙述块并入相邻块，并按标题路径保留层级（存在 `section` 字段）。514 个 chunk 里 narrative 397、table_summary 45、figure 72。数量少不影响召回——12 题评测集 Recall@5 100%。
（`create_data/chunker.py`）

### Q16 图片和图表怎么处理的？

不丢。图表转成摘要文字后和正文一起切分进库，chunk 类型记为 `figure`（72 个），metadata 里带 `img_path`，前端可以回显原图。这样"公司产能布局"这种靠图表达的内容也能被检索到，而不是只能靠正文描述。

## 四、正确性与幻觉

### ★ Q17 "零幻觉"具体怎么做到的？

分两半。**数值**：`sql` 通道根本不经过生成模型——参数化查询出数，模板渲染成文字，直接 `yield` 给前端。只有 `both` 通道才让模型参与，而那时数字已经输出过了，prompt 明令禁止复述。**定性**：走 RAG，但只能引用检索到的片段，片段带公司名和章节，编不出一份不存在的年报。实测 1.5B/1.7B 模型会把"322,045 户"写成"32,204,500 户"——这就是数字不能过模型的直接证据。

### ★ Q18 "不适用"和"未披露"为什么要专门写进 prompt？

财报里"不适用"是**合规标记**：这家公司按规则不需要披露这一项，不是数据缺失。模型会一律说成"未披露"，用户就以为公司在藏数据。同理"否"是对"是否…"问句的否定（"上市时未盈利：否"= 已盈利），"无""-""--"是空格不是 0。这三类标记一旦被当成缺失或数字，答案的专业性直接崩。所以把它写成了 prompt 里的独立段落，不是一句注释。
（`ChatService.COMPLIANCE_RULES`）

### Q19 both 通道为什么先答后补，不把 SQL 和 RAG 一起扔给模型？

因为实测模型会把"推算值"说成"直接披露"，也会顺手改写数字。现在先把 SQL 答案确定性输出完，再起一轮只补定性信息（构成、原因、风险），prompt 里写死"不要复述任何数字，不要重复结论"。这样即使模型发挥过头，坏的也只是补充段落，动不了核心数字。
（`BRIEF_HINT` / `COMPARE_HINT`）

### Q20 答案末尾的"来源：xx §第3节"是模型生成的吗？

不是，是代码从命中片段的 metadata 里取的：`doc_path` + `section`，去重后最多 3 条。原因很直接——模型会编造"来源1"，也会把编号对到错误的句子上。`both` 通道前面已经用"来源："标过数值表，中间那段就换成"参考资料："，避免两组来源混在一起。派生指标（总负债）故意不给来源，因为它是算出来的，没有对应的表。

### Q21 上下文里某个通道为空，为什么不能写"（无）"？

踩过。组装上下文时只拼有内容的通道。如果结构化数据有值、文本通道为空，却写成"文本资料：（无）"，模型会理解成"没查到资料"，然后回答"未披露"——哪怕那一行数字就在上面。空字符串比占位符安全。

## 五、工程与评测

### Q22 为什么用 SSE 不用 WebSocket？

需求是单向推送：用户问一次，服务端流式吐字。没有双向通信，WebSocket 要额外维护连接状态、心跳、重连。SSE 就是普通 HTTP，`StreamingResponse` 吐 `text/event-stream`，反向代理和浏览器都原生支持。代价是只能 GET——这引出下一题。

### Q23 EventSource 不能设 header，JWT 怎么带？

浏览器原生 `EventSource` 只发 GET，加不了 `Authorization`。所以后端做了两级取 token：先读 `Authorization: Bearer`，没有再读 query 里的 `token`，两条路走同一个 `verify_token`。**已知代价**：token 会出现在 URL 和访问日志里，生产环境应该换成一次性短票，这点我在文档里标了是妥协而不是设计。
（`chat/controller/ChatController.py`）

### Q24 LangChain 在这条链路里到底做了什么？不用行不行？

行，但会散。`RunnableParallel` 把通道取数包成可组合单元，`RunnableLambda` 做上下文组装，prompt / llm / `StrOutputParser` 串成一条 `chain.stream()`，流式透传、并发、错误边界都在框架里。手写的话这段会变成一堆 if 加两次独立调用，再手动管理逐块 yield。**要诚实的一点**：这个项目里 `RunnableParallel` 只包了一个 key，属于为结构统一付的一点冗余，真正吃到好处的是 `chain.stream()` 的逐块透传。

### Q25 延迟多少？哪里最慢？21 题评测怎么设计的？

意图 1.1–1.3s；`sql` 通道端到端 1.1–1.3s，`growth` ≈1.2s，`rag` 10–27s，`both` 12–45s。慢在两处：首字前的检索（双路过 50 条 + 20 条 cross-encoder 前向）和云端生成速度；`both` 最慢是因为答完 SQL 还要再起一整轮 RAG + 生成。评测分四层，不是一层：意图裁决 24 条单测、召回 12 题（Recall@5 100%、MRR@10 0.944）、事实恒等式 C1 45/45、端到端 21 题 21/21（覆盖五个通道，断言"通道是否正确"+"答案不能出现拒答词"）。

## 附：三个容易被追问到底的点

| 被问 | 别答 | 应该答 |
|---|---|---|
| MMR 为什么不用 | "会掉点" | 目标函数和需求冲突：λ 趋近 1 等于没用，λ 一降就砍掉同公司不同年份的切片，而那是必须凑满 top-8 的东西；调参救不了 |
| 意图识别为什么用 4B 不用更大 | "显存不够" | 这个任务不需要世界知识，只需要把问题映射到枚举；4B 在结构化输出上足够，且本地跑得起、延迟 1.17s 可接受 |
| 为什么不用微调替代 RAG | "成本高" | 年报数字要求精确，微调只会让模型"更会编"。数值必须走确定性通道，这是正确性问题不是成本问题 |
